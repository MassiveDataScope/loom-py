# ADR 0009: Audit every row change by the person who caused it

- Status: Accepted
- Branch: `feat/postgres-audit-log`
- Applies to: guard revision 3
- Specification: `.specify/specs/008-postgres-audit-log/`

## Context

The database identifies whoever connects: with RDS IAM authentication, the
Lambda's execution role. It cannot identify the person who called the API,
and AWS's trusted identity propagation does not reach RDS or Aurora
PostgreSQL. Products still need to answer "who changed this row, through
which request". Loom already sets per-transaction session keys for row-level
security, so the person can travel the same way to a trigger.

We compared four standard ways to audit Postgres: a row trigger writing an
audit table, change-data capture from the WAL, `pgaudit`, and Aurora's
Database Activity Streams. Only the trigger attributes a change to a person
without new infrastructure; CDC costs least on the write path but needs a
replication slot, a consumer and a per-transaction context row, since the
WAL does not carry the session. `pgaudit` and activity streams record the
database user, not the person.

## Decision

1. **A trigger now, CDC later, one shape.** Each application schema gets an
   `audit_log`, partitioned by month, whose columns are what a CDC consumer
   would produce plus `origin` (`trigger` or `cdc`). Replacing the trigger
   by a consumer changes nobody who reads the log.
2. **Everything that runs in the database is one pinned guard revision,
   `0003.sql`.** No SQLAlchemy `Table` for the log: it has no reader in
   Python, and in the product's Alembic tree an autogenerated downgrade
   would drop the history. Python calls guard functions with bound
   parameters and renders no identifier. The trigger body exists once, as
   `audit_trigger_source()`; the installed `<schema>.write_audit_row()` is
   owned by the schema owner, so the hot path never runs as the installer.
3. **The person travels in session keys** (`loom.actor.subject`,
   `mechanism`, `on_behalf_of`, `loom.trace_id`), set in the same
   `set_config` as the scope keys, on every external Postgres store.
   `on_behalf_of` comes only from the reserved identity attribute
   `loom:on_behalf_of`, which loom's dispatcher writes from what AWS itself
   recorded: an S3 record's `userIdentity.principalId`, or the
   `detail.userIdentity.arn` of an event whose `source` starts with `aws.`.
   JWT claims and configured attributes under `loom:` are dropped or
   refused. Event and schedule triggers must declare an identity, so no
   automatic change runs without an actor.
4. **Append-only for everyone but the trigger.** ACL `{auditor: SELECT}` on
   the log and every partition, with bypass users' default grants revoked on
   each new partition. Row `UPDATE`/`DELETE` and statement `TRUNCATE`
   triggers, `ENABLE ALWAYS`, refuse changes, the owner included; the
   guard's assertion refuses disabling, dropping or detaching any of it.
5. **Retention is the database's decision, not a deploy's.** It lives in the
   guard's configuration, set by bootstrap. `drop_expired_audit_partition`
   refuses a partition within it; `loom schema audit drop-expired` drops one
   partition per run. Without retention nothing is dropped.
6. **Change detection on the whole row.** An update that changes nothing
   records nothing; a change to an excluded or secret column alone is
   recorded as redacted. A failure to record fails the business write.
7. **Deploy steps are commands**: `loom schema bootstrap`, `verify` (exit 1
   on drift) and `audit drop-expired`, each reading its URL from the
   environment.

## Reviews

The placement of the SQL was reviewed on 2026-11-07 by an architecture and a
security reviewer, then the specification, plan and tasks by a council
(Codex, Gemini and the implementing agent). They found that the bypass
default privileges would have granted write access to every partition, that
a row trigger does not see `TRUNCATE`, that a secret-only update would have
left no record, that the existing partition and detach functions would have
let the owner drop history, and that retention applied at deploy could drop
months in one typo. Each became a constraint above, with an integration
test run as the application, the reader, a bypass user and the migrator.

## The future CDC mode

A consumer reads the WAL of audited tables through a logical replication
slot and writes `origin = 'cdc'` rows. The WAL carries the row and its
transaction id, not the session, so each audited transaction would also
write one context row (actor keys, trace, elevation) that the consumer joins
by `txid`. The consumer writes as the schema owner, which can insert into
the log but never change it. Content columns match the trigger's;
`app_name`, `client_addr` and `backend_pid` stay empty.

## Consequences

- About 85 µs per audited row; an unmarked table pays nothing.
- Guard revision 3 is one-way, like every revision.
- The actor keys are claims of the connecting role, as the scope keys
  already are; `db_user`, `client_addr` and `backend_pid` are the evidence.
- Reading the log by person, through an API filtered by row-level security,
  is feature 009; the `scopes` column is captured now so the guard does not
  need another revision for it.
